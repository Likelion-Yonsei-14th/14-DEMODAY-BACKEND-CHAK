# CHAK 팀 논의 사항 정리

> **2026-10-12 갱신**: 아래 C3(작성자 권한)·C4(답장·리액션·신고·차단)·B5(공개 시각)와 D3 중 결제·광고 해제는 백엔드에 **임시 설계로 구현**했다(API 명세 9~10장). 기획·프론트와 확정이 필요하다. 교실(E1)은 지시에 따라 구현하지 않았다. 실제 PG 결제 연동, 친구를 위한 책상(C5), 계정 삭제(D2)는 아직 없다.

> 작성: 2026-10-07 · 백엔드 기준 (코드·DB·프론트 저장소 `14-DEMODAY-FRONTEND-CHAK` 확인 결과)
> 각 항목에 **누가 결정하는지**, **왜 필요한지**, **백엔드 현재 상태**, **제안**을 적었다. 제안은 초안이며 확정이 아니다.

## A. 프론트 ↔ 백엔드 합의 (🔴 P0)

### A1. 카드 JSON 스키마
- **현황**: 프론트 `CardPage`는 `backgroundAssetId`, `textElements`, `wordArtElements`, `stickerElements`, `photoElements`로 구성. 백엔드는 `card.pages[]`(1~3개, 객체)만 검증하고 나머지는 그대로 `LONGTEXT`에 저장(최대 500,000자).
- **결정 필요**: ① 프론트 구조를 그대로 `card`로 저장할지 ② 별도 정규화 스키마를 정의할지. ③ `schemaVersion` 올리는 규칙.
- **제안**: 프론트 구조를 `schemaVersion=1`로 확정하고 백엔드는 구조 검증(필수 키, 배열 크기, 총 크기)만 추가. 요소별 개수 상한도 정한다(예: 텍스트 N개, 스티커 N개).
- **담당**: 프론트 + 백엔드

### A2. 책상 오브젝트 확장 필드
- **현황**: 프론트 `DeskObject`에는 `zone`, `order`, `material`, `charmPhrase`, `gems`, `locked`가 있고 백엔드에는 `x,y,rotation,scale,zIndex,color,assetId,metadata`만 있음.
- **결정 필요**: 확장 필드를 `object.metadata`에 넣을지, 컬럼으로 승격할지. `zone`+`order` 배치와 `x,y` 좌표 중 무엇이 기준인지.
- **제안**: 우선 `metadata`로 수용(백엔드 변경 없음). 조회·필터가 필요한 필드만 나중에 컬럼화.
- **담당**: 프론트 + 백엔드

### A3. 로그인 방식
- **현황**: 프론트는 이메일/Google mock(비밀번호 재설정, 계정 삭제 화면 포함). 백엔드는 카카오만 구현(`POST /api/auth/kakao`). 프론트 문서도 "Kakao login 포함 여부"를 미확정으로 둠.
- **결정 필요**: 카카오 단독 / 카카오+Google / 이메일 포함 여부. 이메일 가입을 넣으면 비밀번호 저장·재설정·이메일 인증·발송 인프라가 백엔드에 새로 필요.
- **제안**: 수험생 대상 + 카카오 공유 링크 중심이므로 카카오 단독으로 MVP. 이메일/Google 화면은 제거하거나 후순위.
- **담당**: 기획 + 프론트 + 백엔드

### A4. 책상 링크 라우팅과 토큰
- **현황**: 프론트가 `/prototype/support/jisu`로 하드코딩. 백엔드는 `supporterToken`(UUID)으로 조회.
- **결정 필요**: 공유 URL 형식(예: `/desk/:supporterToken`), 책상 이름·도메인 노출 정책, 토큰 재발급(유출 시) 필요 여부.
- **제안**: `/desk/:supporterToken`. 토큰 재발급 API는 출시 후.
- **담당**: 프론트 + 기획 + 백엔드

### A5. 인증·통신 규약
- **토큰 저장**: access/refresh는 응답 본문 전달. 프론트가 어디(메모리/localStorage)에 저장할지. XSS 위험과 새로고침 유지 사이 트레이드오프. refresh를 HttpOnly 쿠키로 바꾸려면 백엔드 변경 필요.
- **401 처리**: 공개 API도 만료 토큰이면 401(문서화됨). 프론트 공통 인터셉터에서 refresh 후 재시도할지 합의.
- **프론트 반영 확인**: `SliceResponse`(page/size/hasNext), 트래픽 `eventId`(고유값, 재시도 시 동일), 광고 `sessionId`(노출마다 새로, 재시도 시 동일).
- **로컬 개발**: Vite proxy 또는 CORS 직접 호출 중 선택. 현재 백엔드 기본 허용 Origin은 `localhost:3000/5173`.
- **Vercel 프리뷰 도메인**: 프리뷰 URL이 배포마다 바뀌는데 백엔드 CORS는 와일드카드를 허용하지 않음. 프리뷰에서 API를 쓸지, 쓴다면 패턴 허용(`*.vercel.app` 등) 도입 여부 결정.
- **에러 코드 분기표**: 프론트가 `code`별 UI(토스트/화면)를 정해야 함. 필드별 검증 메시지는 현재 없음(필요하면 백엔드 확장).
- **담당**: 프론트 + 백엔드

## B. 백엔드 내부 · 기술 (🟠 P1)

### B1. 배포·인프라
- 호스팅(서버), MySQL(관리형 여부), 도메인, HTTPS, 로드밸런서·게이트웨이, 환경 분리(dev/staging/prod).
- 실제 MySQL에서 Flyway 마이그레이션 리허설(현재 테스트는 H2). 기존 Hibernate 생성 DB가 있으면 README의 baseline 절차 1회 수행.
- 자동 배포(CI/CD)와 롤백 방법. 현재 `main`에 직접 push한 이력이 있어 브랜치·리뷰 규칙도 정리 필요.

### B2. 시크릿·보안 설정
- `JWT_SECRET` 기본값이 코드에 있음. 운영에서 기본값 그대로 뜨는 사고를 막으려면 **운영 프로필에서 기본값이면 기동 실패**하도록 가드 추가 필요.
- 비밀값 관리 방식(환경변수 vs 시크릿 매니저), 키 로테이션.
- 액세스 토큰은 로그아웃 후에도 만료(30분)까지 유효. 허용 가능한지 확인.
- Swagger UI를 운영에서 열어둘지(현재 공개).

### B3. 스팸·어뷰징 방어
- 편지 작성 자체에는 rate limit이 없다(이벤트 기록만 분당 120건). 비회원은 쿠키 삭제로 우회 가능.
- 게이트웨이/IP 단위 제한, 닉네임·본문 욕설/광고 필터, 신고 접수 후 처리 흐름.
- 사진·텍스트 유해 콘텐츠 정책(수험생=미성년자 다수).

### B4. 이미지 정책 (기존 TODO)
- **비회원 이미지 첨부: 금지로 결정(2026-10-12).** 백엔드가 `403 GUEST_IMAGE_NOT_ALLOWED`로 거부하고 프론트는 로그인 안내를 보여준다. 아래는 회원 사진에 대한 남은 결정이다.
- **공개 편지의 이미지를 비로그인 방문자가 볼 수 있어야 하는가**: 현재 다운로드 URL은 자산 소유자만 발급 가능 → 다른 사람 편지 이미지는 볼 수 없음. 프론트 `PhotoElement`는 사진 편지를 전제로 함.
- 선택지: ① 편지에 연결된 이미지는 책상 주인·공개 범위에 따라 서명 URL 발급(권한 모델 추가) ② 공개 CDN 사용(영구 공개 URL 금지 원칙과 충돌) ③ 사진 첨부는 회원만.
- 운영: S3 `tmp/` 수명 주기 삭제, 미완료 업로드 정리, 이미지 삭제 API, 용량·비용 상한, 이미지 리사이즈/썸네일.

### B5. 공개 시각 계산 규칙
- **현황(확인됨)**: 편지 `unlockAt`은 작성 시점에 계산해 저장하고, 책상 설정에서 `readModeType`/`dailyUnlockTime`/`capsuleUnlockAt`을 바꿔도 **기존 편지의 `unlockAt`은 재계산되지 않는다**.
- **결정 필요**: 설정 변경 시 기존 편지에 적용할지(공개 시각을 앞당기거나 미루는 것이 허용되는지), 이미 열린 편지가 다시 잠기는 것을 허용할지.
- 기획 의도(수능 당일 열람 등)와 맞는지 확인 후 백엔드 반영.

### B6. 품질·운영
- 테스트: 실제 MySQL(Testcontainers) 통합 테스트, E2E, 권한/동시성 테스트 확대.
- 로깅·모니터링·알림, 에러 추적, 헬스체크 연동(`/api/public/health` 추가됨).
- API 변경 정책: 브레이킹 체인지 공지 방식, OpenAPI에서 프론트 타입 자동 생성 도입 여부.
- 관리자 광고 목록 페이지네이션(현재 전체 반환), 관리자 지정 방식(환경변수 `ADMIN_KAKAO_IDS`).

## C. 기획 · 디자인 · 프론트 · 백엔드 (🟠 P1)

### C1. 책상 방문자에게 무엇을 보여줄 것인가
- **현황**: 공개 편지 API는 `PUBLIC`이고 열린 편지만 반환. 프론트 책상 장면은 방문자에게도 오브젝트(편지, 부적 등)를 보여주는 구조이고 "부적 문구는 모두에게 보임"이라고 명시.
- **결정 필요**: 비공개·잠긴 편지의 **오브젝트(봉투 모양과 위치, 작성자 이름 포함 여부)** 를 방문자에게 노출할지. 노출한다면 `card` 없이 오브젝트만 주는 공개 API가 새로 필요.
- 작성자 이름·개수 노출은 프라이버시와 응원 동기에 모두 영향.

### C2. 편지 공개 범위 규칙
- 기본값 PRIVATE이 맞는지, 작성자가 작성 시점에 선택하는 UX(프론트 `VisibilitySheet`)와 책상 주인의 `defaultMessageVisibility`가 충돌할 때 우선순위(현재: 요청값 우선, 없으면 책상 기본값).
- 주인이 공개 범위를 일괄 변경할 수 있다는 점을 작성자에게 고지할지(작성자가 PUBLIC으로 쓴 편지를 주인이 PRIVATE로 바꿀 수 있음).

### C3. 작성자 권한과 편지 철회
- 프론트에 "보낸 응원" 화면과 "내가 보낸 공개 응원 삭제"가 있음. 백엔드에는 **작성자용 조회·삭제 API가 없음**.
- **결정 필요**: 작성자가 보낸 편지를 조회·삭제·수정할 수 있어야 하는가. 비회원은 쿠키로만 식별 가능(쿠키 분실 시 접근 불가). 열람 전 철회 허용 범위.

### C4. 답장 · 리액션 · 신고 · 차단 (프론트 구현됨, 백엔드 없음)
- MVP에 포함할지, 포함한다면 도메인 설계(주인의 일방향 답장 `single/daily` 범위, 리액션 3종, 차단 대상=닉네임 vs 계정/쿠키).
- 신고 접수 후 운영자 처리 방식(관리자 화면, 처리 기준, 알림). 닉네임 기반 차단은 비회원이 이름을 바꾸면 우회됨.

### C5. 타인을 위해 만든 책상과 소유권 이전(Claim)
- **현황**: 프론트에 `createdFor: self | other`, `claimStatus`, Claim 화면이 있음. 백엔드는 DB에 `creator_id`, `claim_status`가 있고 `createUnclaimed` 도메인 메서드도 있으나 **API는 본인 책상 생성만** 있음.
- **결정 필요**: MVP에서 "친구가 대신 책상을 만들어주는" 흐름을 지원할지. 지원한다면 Claim 토큰 설계, 이전 후 생성자 권한(프론트 문서: Claim 후 별도 관리 권한 없음), 클레임 전 쌓인 편지 처리(`preclaim_backlog`).
- 계정당 책상 1개 제약과 "남을 위한 책상"이 충돌하는지 확인(소유자가 없는 동안은 creator 기준).

### C6. 비로그인 재방문
- 프론트 문서에서도 미확정. 카카오톡 인앱 브라우저는 쿠키 저장소가 분리되어 같은 사람을 못 알아볼 수 있음. 비회원이 자기 편지를 다시 찾는 경로(C3)와 직결.
- 선택지: 쿠키만 / 로그인 권유 / 개인 관리 링크 발급.

### C7. 로그인 강제 시점
- 현재 백엔드: 공개 책상 조회·편지 작성은 비로그인 가능, 책상 생성·관리는 로그인 필수. 편지 작성 후 "가입하면 내 편지 관리" 같은 전환 유도 시점을 기획이 정해야 함.

## D. 기획 · 법무 · 운영 (🟠 P1)

### D1. 개인정보·약관
- 수집 항목: 카카오 닉네임, 이메일(선택 동의), 프로필 이미지. 비회원: 쿠키 식별자, 편지 내용, 분석 이벤트.
- **만 14세 미만 가입** 처리 방침, 개인정보처리방침·이용약관·동의 UI, 카카오 동의항목 설정.
- 편지 내용은 제3자(책상 주인)에게 공개되는 개인 콘텐츠 → 작성자 고지 문구.

### D2. 계정 삭제·데이터 보존
- 프론트에 계정 삭제 화면이 있으나 **백엔드 탈퇴 API 없음**. 탈퇴 시 본인 책상, 받은 편지, 보낸 편지(익명화/삭제), 이미지, 리프레시 토큰을 어떻게 처리할지.
- 시즌성 서비스이므로 **수능 후 데이터 보존 기간·파기 정책**을 정해야 함.

### D3. 광고·결제
- 프론트는 "광고 시청 후 편지지 해제", 유료 부적/스티커/보석(50원, 5원 등)을 mock으로 구현. 백엔드 광고는 노출·시청·클릭 기록만 있고 **해제 검증·구매·결제·소유 상태 저장 없음**.
- 결정 필요: 광고 네트워크 선택(자체 광고 vs 외부), 시청 완료 검증 방식(클라이언트 신뢰 여부), 결제 수단·PG, 구매 항목 저장 모델, 환불 정책. 가격은 프로토타입 값(최종 아님).
- 이 기능은 규모가 커서 MVP 포함 여부부터 확정 필요.

### D4. 알림
- 프론트에 푸시 설정 UI가 있음. 채널(카카오 알림톡/웹푸시/이메일)·빈도·공개 시각 알림 필요 여부 미정. 백엔드는 알림 인프라 없음.

### D5. 상표·콘텐츠 권리
- 대학 깃발·굿즈 부적 등 학교 이름을 쓰는 유료 상품은 상표 사용 허락 문제(프론트 문서에도 미확정). 서비스명/브랜드명도 미확정.

### D6. 통계·분석 요구
- 운영자가 보고 싶은 지표 정의(DAU, 초대 링크 유입→편지 작성 전환율 등). 현재는 이벤트 종류별 건수 합계만 제공하며 일별 집계 테이블은 없음.
- 분석 이벤트 보존 기간, 개인정보 최소화(IP/UA 원문 미저장은 현재 원칙).
